مِرصاد V17 — إصلاح استمرار السحب الجماعي تلقائيًا
السبب
كانت لوحة `multi_group_panel` تفحص `st.session_state[multi_running_<id>]` قبل تشغيل كل دورة، وهي قيمة مؤقتة تضيع بعد إعادة تحميل الصفحة أو إعادة تهيئة جلسة Streamlit، حتى عندما تكون حالة المجموعة المحفوظة في SQLite هي «قيد التشغيل».
ما تغير
`app.py` فقط: حالة المجموعة في SQLite (`target_groups.status`) أصبحت المرجع الأساسي لتشغيل الدورات المتسلسلة.
عند إنشاء المجموعة والتحقق من يوزراتها يبدأ التنفيذ من نفس زر «إنشاء مجموعة الحسابات»، دون الحاجة لضغطة تشغيل ثانية.
عند الضغط على «بدء / استكمال المجموعة» تستمر دورة السحب والتناوب وإثراء About عبر تحديث fragment كل ثانيتين، ضمن سقف طلبات RapidAPI.
بعد إعادة تحميل صفحة المجموعة، يستأنف fragment تحديث الدورات إذا بقيت المجموعة في قاعدة البيانات بحالة «قيد التشغيل».
اختيار «إيقاف المجموعة» يوقف التنفيذ عمدًا ويحفظ التقدم.
عند توقف حساب بسبب خطأ حقيقي، تظل الحسابات الأخرى التي في حالة «جاهز» قيد المعالجة؛ وتعرض الواجهة سبب الخطأ بدل المطالبة المتكررة بالضغط.
مؤشر حي لعدد المتابعين المكتشفين والمهام المكتملة، ورسالة انتظار عند استهلاك حصة الطلبات.
كل دورة تفتح اتصال SQLite مستقلًا وتغلقه بعد انتهاء الدورة.
التثبيت
احتفظ بنسخة احتياطية من `app.py` وقاعدة البيانات.
ارفع `app.py` من هذه الحزمة إلى جذر مستودع GitHub واستبدل النسخة الحالية.
لا تستبدل `multi_accounts.py` أو `rapid_client.py` بالإصدارات القديمة: احتفظ بإصلاح المرحلة الثانية وإصلاح استجابة المزود الأخير.
بعد Commit، افتح الموقع في صفحة «سحب متابعي X ← مجموعة حسابات» وجرّب مجموعة صغيرة.
الحدود
هذا إصلاح لتشغيل الواجهة، وليس عاملًا دائمًا على خادم منفصل. يتطلب استمرار صفحة Streamlit وجلسة المستخدم فعالتين؛ قد يوقف المتصفح تحديثات التبويب غير النشط.
إذا أعاد RapidAPI خطأ مستمرًا أو انتهت الصفحات بحد حماية، ستتوقف المهمة المتأثرة عمدًا ولا نعيد الطلبات بلا حد.
قاعدة SQLite المحلية على Streamlit Community Cloud ليست تخزينًا دائمًا مضمونًا.
الاختبار محلي (صياغة وفحص منطق)، ولم يُختبر على RapidAPI الحي أو موقع الإنتاج.
